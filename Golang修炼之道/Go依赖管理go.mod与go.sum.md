# Go 依赖管理笔记：`go.mod` 与 `go.sum`

**1. `go.mod` 中为什么有两个 `require` 块？**

主要是为了区分直接依赖和间接依赖，便于阅读：

| 类型     | 标记               | 含义                                                 |
| -------- | ------------------ | ---------------------------------------------------- |
| 直接依赖 | 没有 `// indirect` | 项目代码或测试直接导入了该模块中的包                 |
| 间接依赖 | 带 `// indirect`   | 项目通过其他依赖间接使用该模块，没有直接导入其中的包 |

注意：

- `require` 声明的是**模块（module）**，一个模块可以包含多个**包（package）**。
- 两个块没有优先级区别，也不是必须分成两个块。
- **决定直接、间接属性的是实际导入关系，不是放在第几个块。**
- `go mod tidy` 会根据实际依赖关系整理依赖和 `indirect` 标记。

**2. 第一个块中的模块依赖的所有模块，都会出现在第二个块吗？**

**不会。第二个块不是第一个块的完整下游依赖清单。**

例如：

```
你的项目
├── 直接使用 A
│   └── 使用 B
│       └── 使用 C
└── 直接使用 C

A 中另一个未被项目使用的包
└── 使用 D
```

通常整理后：

```
直接依赖：A、C
间接依赖：B
D：不一定需要记录
```

原因：

- C 虽然也被间接使用，但项目直接使用了它，因此归为直接依赖。
- 项目不需要使用 A 中的所有包，未涉及的包所依赖的 D 不一定需要记录。
- 标准库，例如 `fmt`、`net/http`，不写入 `require`。
- 间接依赖可以跨多层，不只包含“下一层”。

**3. `replace` 的作用是什么？**

**用指定来源的代码替代某个模块，源码中的导入路径通常不变。**

项目中的例子：

```
// 声明项目对 Gin 模块的版本要求。
require github.com/gin-gonic/gin v1.10.0

// 使用内部仓库的指定版本替代 Gin 的实现。
replace github.com/gin-gonic/gin => git.yukework.com/pkg/gin v1.9.1-zyb5
```

含义：

```
代码中的导入路径：github.com/gin-gonic/gin
实际使用的代码：git.yukework.com/pkg/gin v1.9.1-zyb5
```

要点：

- `replace` 左边不写版本，表示替换该模块的所有版本。
- 只提高 `require` 中的版本、保留上述替换规则，实际源码仍来自右侧的固定版本。
- 替换目标可以是另一个模块版本，也可以是本地目录。
- 不能只看 `require` 判断实际使用的代码，还要看 `replace`。

**4. `go.sum` 的作用是什么？怎么阅读？**

**`go.sum` 保存模块内容的校验值，用于检查下载内容是否一致。它不负责选择依赖版本。**

每行格式：

```
模块路径    版本（可能带 /go.mod）    校验值
```

例如：

```
github.com/samber/lo v1.47.0 h1:……
github.com/samber/lo v1.47.0/go.mod h1:……
```

| 记录形式         | 校验对象                      |
| ---------------- | ----------------------------- |
| `v1.47.0`        | 该版本的模块内容              |
| `v1.47.0/go.mod` | 仅该版本的 `go.mod` 文件      |
| `h1:……`          | 基于 SHA-256 算法生成的校验值 |

`/go.mod` **不是另一个版本**。Go 有时只需读取依赖声明，无须下载完整源码，因此某个版本可能只有 `/go.mod` 校验记录。

**5. `go.sum` 和 `go.mod` 怎么对应？为什么多出很多模块？**

**它们不是一一对应的。**

没有替换时，按“模块路径＋版本”查找；存在 `replace` 时，还要看替换目标：

```
go.mod 声明 Gin v1.10.0
    ↓ replace
内部 Gin v1.9.1-zyb5
    ↓
go.sum 保存内部模块该版本的校验值
```

`go.sum` 的内容由依赖解析、下载、历史操作和整理规则共同决定：

| 原因              | 可能出现的记录                   |
| ----------------- | -------------------------------- |
| 解析模块依赖图    | 只读取过 `go.mod` 的模块或版本   |
| 下载模块内容      | 模块内容的校验值                 |
| 升级、删除依赖    | 尚未清理的旧版本记录             |
| Go 版本及兼容规则 | 为解析兼容的依赖图而保留的校验值 |

关键区别：

> **读取过某个模块的依赖声明，不等于项目使用了它的源码；出现在 `go.sum` 中，也不等于它是当前选中的版本。**

因此，不要仅凭“`go.mod` 没有这个模块”就手工删除校验记录。

**6. 为什么有的版本是 `v1.9.2`，有的是很长的一串？**

这是两种版本标识方式，**与是否为 `indirect` 无关**。

| 形式                                 | 名称           | 含义                               |
| ------------------------------------ | -------------- | ---------------------------------- |
| `v1.9.2`                             | 普通语义化版本 | 通常对应仓库中的版本标签           |
| `v0.0.0-20240227163752-401108e1b7e7` | 伪版本号       | 标识没有对应合适版本标签的具体提交 |

普通版本号：

```
v1.9.2
 │ │ │
 │ │ └── 补丁版本
 │ └──── 次版本
 └────── 主版本
```

伪版本号：

```
v0.0.0 - 20240227163752 - 401108e1b7e7
基础前缀    提交时间          提交哈希前缀
```

这个例子中：

- 时间为 **2024 年 2 月 27 日 16:37:52 UTC**，不是下载时间。
- `401108e1b7e7` 是 Git 提交哈希的前 12 位。
- 伪版本由 Go 工具生成，并不一定以 `v0.0.0` 开头；存在合适的祖先版本标签时，会基于该标签生成。
- 伪版本标识固定提交，不会自动跟随仓库最新代码。

**7. 常用检查命令**

```
# 查看当前选中的模块版本及替换关系。
go list -m all

# 预览依赖整理差异，不修改 go.mod 和 go.sum；适用于本项目的 Go 1.23。
go mod tidy -diff

# 根据实际依赖关系整理文件，会修改 go.mod 和 go.sum。
go mod tidy
```

**记忆对照：**

| 内容             | 回答的问题                         |
| ---------------- | ---------------------------------- |
| `require`        | 对哪些模块有什么版本要求？         |
| `// indirect`    | 是否通过其他依赖间接使用这个模块？ |
| `replace`        | 实际用哪里的代码替代它？           |
| 普通版本／伪版本 | 用标签还是具体提交来标识代码？     |
| `go.sum`         | 下载内容是否与记录的校验值一致？   |

另外，`require` 中的版本通常是**最低版本要求**，最终选中的版本可能因其他依赖的要求而提高；检查实际选择结果时，看 `go list -m all`。
